# Rivo 0.8.7-rivo.4

A defect pass over the player, the downloads queue and the update check. No new screens.

## SponsorBlock and subtitles actually run

Both features were wired end to end and produced nothing, which is the worst kind of broken:
the switches were on, the UI responded, and the result never showed up.

The SponsorBlock lookup read `/api/skipSegments?videoID=…` as if it answered
`[{videoID, segments: [...]}]`. That shape belongs to the hash-prefix endpoint; the per-video
one answers with a flat array of segments. Decoding the flat array into the wrapper produced an
empty list with no error, so no video ever had a skip or a band on the timeline. Even after that,
the segments arrived after the media item was built, so the bands were missing until a quality
change rebuilt it. Both are fixed: the flat response parses, and the lookup finishes before the
item is prepared (bounded at 1.5 s so a slow API cannot delay playback).

Subtitles had the same shape of bug. Every resolved stream is built by `StreamMediaSourceFactory`
— HLS, DASH, progressive, merged video+audio — and none of those branches ever looked at the
item's subtitle configurations, because only `DefaultMediaSourceFactory` merges them. The
captions sheet listed the languages, the chip flipped to `CC es`, and no caption was drawn. The
sidecars are now merged exactly the way Media3's own factory does it, so the track the sheet
offers is the track that renders.

## The first seconds of a playlist

Next and Previous were gated on `hasNextMediaItem()`, which only reports the prefetch window —
one item ahead. On a 26-item queue the header said "1 of 26" while Next did nothing, because
item 2 had not finished resolving yet. Next now asks the service to resolve and append the next
item, and the end-of-item prefetch waits for an in-flight pass instead of returning early, so a
track that ends while the next one is still loading advances instead of parking at the end.

## Recovery that stays available

An item's single retry was consumed before the retry ran, so a retry that failed to obtain a
fresh URL burned the budget for the rest of that video, and left the player sitting on the
error. The budget is now spent by a successful retry, and a failed recovery moves on to the next
item instead of freezing.

## Small, real ones

- A chapter tap could jump to the start: the seek clamped against a duration that is `0` until
  the player knows it. The clamp only applies once a duration is known.
- VLC handoffs now get the documented `position`, `from_start` and `title` extras, so "resume
  at" and the title survive.
- The update check's six-hour window is stored in preferences instead of only in memory, so a
  cold start does not mean one request to GitHub per launch. A pending release is not stored,
  so it is re-checked rather than hidden for six hours.
- A corrupt `queue.json` is moved aside as `queue.json.corrupt` instead of reading as an empty
  queue and then being overwritten with the next task.
- The download archive takes a lock, empty cache directories are actually removed, and removing
  an item that is not in a playlist no longer reorders the playlist list.

## Also

`docs/PARITY.md` names `CONFIG_VLC_ARGS` as preserved-but-inert (VLC accepts no libVLC options
through `ACTION_VIEW`) and says why a VLC/MX handoff loses the remote subtitle sidecars.
